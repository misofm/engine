# A plan's lane-swap defect and carry-refusal totals reach hosts as one accumulating wire counter

**Decision (2026-11-09):** made by root under the owner's explicit delegation of 2026-11-09 ("reason about it and proceed"), for issue #2425, the question #2419 recorded. Authority kind: owner-delegated answer.

**Ruling: yes, on the wire, as one ID.** One new frozen `protocol::CounterId`, `BankContractDefects = 23`, counts, over every plan the session adopted, the bank-contract defects the engine contained: every recovery `graph::lane_swap_defect_count` counts (#2414, #2419) and every refused restore `graph::carry_refusal_count` counts (#1279 D6). It is a non-resetting counter like every other served ID: it accumulates across plan replacements and reads 0 from construction. It is 0 in a correct build. The two in-process functions stay, unchanged, as the per-plan readers for tests, the #1286 cost record and the #2424 rebuild. This ruling records the decision; the implementation is a separate issue whose spec is filed with it.

## The case
Two per-plan totals say that a console or insert bank broke its lane contract at render time and that the engine contained it. A stranded or split lane swap reset two lanes to their prepared defaults and pinned both strips (#2419); a refused carry left one lane as prepared, at rest (#1279 D6). Both are reads over `&mut PreparedRenderPlan`, so only a process that holds the plan can read them. The browser Worker hands the render half to the AudioWorklet and holds no plan; a C-ABI app reads counters only through `CounterId`. In production, therefore, neither host can know that a defect happened. #1279's review recorded exactly this ("nothing in production reads `carry_refusal_count`", NIT 4) and root's 2026-10-12 ruling surfaced the total in #1286's descriptive bench record, which no host reads. #2419 kept the lane-swap total beside it with the same reach and asked for this ruling.

## What a host needs
A host cannot repair a bank. What it can do with the number is exactly two things:
1. **Report.** A nonzero count is a defect the gates did not catch, found in the field. The engine's developers learn of a field defect only through what a host reports, and a host reports what the counter snapshot contains. This is the need `TransitionReprepareRefusals` (17) and `LiveBlockErrors` (19) already serve: both "stay 0 in a correct build" and both are wire counters, because a fallback decided after submit returns has to be visible to the host (decision 15, D15-17). A bank-contract recovery is such a fallback: render decided it, after the fact, on the host's audio.
2. **Account for a restart it was not told about.** `StripsRestarted` (18) tells a host which strips started at rest at an adoption, so an app can explain a transient. A refused carry puts a lane at rest without being listed; a lane-swap reset puts two lanes at their defaults in the middle of a plan's life. Without this counter, a host that reconciles restarts against 18 finds a restart that nothing explains.

Triggering the repair is **not** a host need: #2424 makes the engine rebuild on a nonzero lane-swap total through the existing control-plane path, because the engine holds the plan, the bound and the pin, and a host does not. So this counter is read-only observability, never a signal a host must poll to keep the engine correct.

## Why one ID, and why both totals in it
- **The host's use is the same for both.** Report, and reconcile a restart. Nothing a host can do differs between a stranded swap and a refused carry; two IDs would be granularity nobody acts on, bought at two permanent wire identities. The in-process functions keep the two apart where the difference matters: #2424 rebuilds on the lane-swap total only (a refused carry leaves no residue; the plan it happened in is already the fresh one), and tests pin each mechanism separately.
- **The claim is one claim.** "No bank broke its contract in this session" is the thing a nonzero value falsifies, and AGENTS.md keeps a count that *is* the claim exact. The unit is contained defects: a recovery for the lane-swap total (one slot that strands on its swap-back counts twice, as #2419 defines), a refused lane restore for the carry total. The mixed unit is acceptable because the counter is a defect tally, not a resource measure; its doc says what one count is.
- **Accumulating, not per plan.** Every served counter is non-resetting (#1351 D1) and a per-plan value cannot be one: a host would miss every plan it did not read in time, which is the acked-batch shape of error (a fact that advanced and then vanished). The per-plan values stay in-process.

## Cost, and why it is paid
A new ID is frozen for the life of the protocol (#1629 retires, never reallocates). The price is one enum arm and its decode row, one slot in host-core's served array, one line in `refresh_provider_counters` (which already says "a counter added later joins this refresh, never a single control call"), one documented line in `miso_engine_v1.h`, one SDK fixture name, and one parity row per host. It adds no C symbol, no struct and no feature bit. The identity will not go dead: banking is the engine's permanent render architecture, the lane swap and the carry are permanent parts of it, and making a swap infallible by type is a stated non-goal of #2414, #2419 and #2424. A counter whose defect class is permanent and whose readers are the two shipping hosts earns its ID; what would not earn one is a per-plan diagnostic that only a test reads, which is what the two in-process functions remain.

## Render cost: none on a healthy block
The value is never maintained per block. The implementation chooses between two reads, both off the render thread's healthy path:
- **At reclaim.** `synchronize_plan_epochs` (control plane) owns each retired `PreparedRenderPlan` exclusively before it drops it; the two functions can be read there at no render cost. Its weakness is lag: the active plan's defects are not counted until it retires, which for a refused carry can be the rest of the session.
- **A mirror written on the defect path only.** The pattern of `live_block_errors` (#1521 D3): an atomic the render side stores into only on the path that already reset a lane, so a healthy block runs no new instruction; the control plane reads it into the snapshot at `refresh_provider_counters`. This is the read the ruling prefers, because it is current by the first control call after the block that incurred the defect, and because #2424 is about to build the same defect-path signal for its rebuild flag; one path carrying both the flag and the count is the correct long-term shape.

Either way the counter must be exact (no defect double-counted across a plan's reclaim and its mirror) and the implementation records which read it took and its lag.

## Rejected options
- **No wire counter; the engine acts (#2424) so no host needs the number.** Rejected because acting and reporting are different needs. A rebuild repairs the residue; it does not tell the host that its audio took a defect, and a rebuild storm bounded in process is still invisible to the people who would fix the bank. It also leaves the carry total with no reader at all, since no rebuild follows a refused carry. This is the shape that deferred #1279 NIT 4 twice; deferring it a third time, with the two shipping hosts unable to see a defect class the engine recovers from by design, is the kind of shortcut AGENTS.md rules out.
- **Two IDs, one per total.** Rejected above: no host acts differently on them.
- **Fold into `StripsRestarted` (18).** Rejected: 18 has a frozen meaning (#1768: the strips preparation listed, reported once by the adopting render), a lane-swap reset is two lanes mid-plan and not a strip at adoption, and folding a defect into a planned-restart count hides the defect.
- **A watermark outcome flag.** Rejected: outcome flags are the OR over the revisions a watermark advance covered (D15-17), and a packer episode's stranded swap belongs to no revision. A refused carry does belong to the adopting revision, but the flag set is frozen to the control plane's own fallbacks and a flag cannot carry a count.
- **A per-plan value on the wire.** Rejected: not a non-resetting counter, and a host that misses the plan's lifetime misses the defect.
- **Make #2424 count defect-driven rebuilds on the wire instead.** Rejected as the host-facing surface: a rebuild is the engine's remedy, not the host's fact. #2424's rebuild tally and bound stay in process and tested; a host sees a defect-driven rebuild as this counter rising together with the plan epoch advancing. #2424 therefore needs no wire ID of its own.

## Constraints on #2424
#2424 is not blocked by, and does not implement, the wire counter. It keeps reading `graph::lane_swap_defect_count` in process, rebuilds on the lane-swap total only, adds no `CounterId`, and builds its render-side flag on the defect path so the counter issue can carry the running total through the same path. Its "the rebuild is visible" gate is met in process (a tested tally and bound) until the counter lands, and then by the counter.

## Reopening condition
Reopen if a product need appears for a host to tell the two totals apart, for example an app that must know whether a strip's defaults are its own (a carry refusal) or possibly another strip's (a lane-swap defect before its rebuild). That reopening must show what the host does differently, and it allocates a new ID rather than changing 23's meaning.

## Where it is pinned
`protocol::CounterId::BankContractDefects` and its decode row, once the implementation issue lands; the protocol's frozen-ID tests; one host-core test that strands a swap (as #2419's tests do) and reads the counter through the provider; one parity row each in `capi` and `host-web`. Until then, the per-plan readers are `graph::carry_refusal_count` and `graph::lane_swap_defect_count` in `crates/graph/src/lib.rs`.
