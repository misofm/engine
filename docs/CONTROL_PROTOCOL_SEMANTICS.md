# MISO control protocol semantics

This defines controller behavior for the [BTLV bytes](CONTROL_BTLV_V1.md) and [registry](CONTROL_PROTOCOL_REGISTRY.md). It does not publish a plan, execute a seek, define DSP parameter meanings, or transport PCM.

## Revision, transaction, and replay

The committed `SessionModel` owns its revision, and the revision lies in `0..=9223372036854775807` (2^63 - 1, the session schema's domain; the wire field stays `u64`); command `revision-any` is therefore the header flag plus a zero carrier, never a revision sentinel. Structural edits require an exact revision and at least one edit; a configured zero edit limit disables the transaction command and its paired session events in capabilities and dispatch. Transactions clone/apply/compile a candidate typed session and replace `(SessionModel, CompiledSession, SessionRevision)` only when all validation, capacity reservation, and compilation steps succeed. One success increments once; malformed input, empty input, validation/compile/resource failure, backpressure, and replay leave model and revision untouched. A mutation at revision 2^63 - 1 returns `REVISION_EXHAUSTED` before the candidate is built; the controller does not turn a compiled session into a `PreparedRenderPlan`.

A transaction that needs a new plan while an earlier one's replacement plan is still unadopted commits as any other (#1310): the host takes the waiting replacement back, prepares one successor of the running plan that carries both, and publishes it, or, should the new transaction be refused, publishes the waiting replacement again unchanged. Host-fed sources the earlier transaction added keep their accepted PCM and queued seeks. No accepted chunk is dropped across a supersession: when the waiting replacement created a source's ring (the earlier transaction added the source, or redeclared it) and the host has fed that ring (a chunk, a seek or an end of region), a new transaction that does not keep the source as the replacement declares it (it declares it as the running plan does, redeclares it another way, or removes it) is refused with backpressure before it commits. Nothing changes (the replacement stays published, no event, no revision), and a retry after render adopts the replacement commits. A host that does not render keeps getting backpressure for such a transaction until it renders. A source the replacement carries unchanged from the running plan is not refused this way. Every case stays refused, the one where the new transaction declares the source as the running plan does included (#1698): the host restarted its feed of the source against the waiting replacement, so the successor starts the source fresh and cannot play that replacement's chunks; the cases stay refused until an issue lets the successor read those chunks or the owner rules that a removed source's chunks may drop. Everything else the new transaction leaves as the running plan has it (a strip, an effect, a meter) carries from the running plan as one direct transaction would carry it, also when the waiting replacement had restarted or removed it (#1698). A source the caller's own transaction removes discards its queued audio, whether the running plan or the waiting replacement (carrying it unchanged from the running plan) holds it: the caller asked for the removal, so this is not an unintended drop. The session counter `SOURCE_FRAMES_DISCARDED` (21, #1699) counts those frames: when the service step reclaims a displaced plan, every source ring that plan still holds (a ring the successor carried left it, so what remains was removed or redeclared) adds the frames of its queued chunks, a stale-generation chunk included, and of its popped but unplayed chunk. A failed carry (the successor could not take the running plan's rings, `CarryOutcome::PredecessorMismatch`) loses the frames of every ring it did not move, and those are counted too. Frames render played, session destroy and a withdrawn replacement's own rings (refused if fed, above) add nothing. The applied-revision watermark completes the displaced revisions as `superseded` when the successor is adopted. The resource admission counts every plan the session still holds (the running plan, the waiting replacement, and a plan render has displaced until the service step reclaims it) and the successor. A resource refusal is backpressure when the successor fit against the newest held plan alone, so a retry after a render normally commits; the split is approximate, and such a retry may still be refused within a small band (a successor prepared on the adopted replacement differs by a few hundred bytes from one prepared across it). It is a compile rejection when the successor does not fit even then.

All v1 operations are absolute and idempotent. A new logical command has a nonzero, strictly increasing endpoint-local request ID. The bounded replay cache stores exact canonical request and response bytes. Identical repeated bytes return the cached response without execution; same ID with changed bytes returns `REQUEST_ID_REUSE`; evicted/retired IDs return `REPLAY_EXPIRED`. Completed backpressure is replayed too, so retrying it uses a new ID. Cache capacity is reserved before execution; an unretainable response is rejected before state changes. The guarantee ends with the endpoint lifetime; reconnect recovery belongs to an adapter.

## Session replace (#1386)

`SESSION_REPLACE` (`0013`) replaces the whole session with a document while it plays, as the one transaction the document's diff against the committed model gives: the same revision, edit path, events and rendered bits as that `SESSION_TRANSACTION_APPLY`. A host with a document transport serves it through the one core path (`SessionState::command_with_document`) and no host decodes the frame or runs replace code; the C ABI does today, and the browser, which has no transport until #1697, neither advertises it nor serves it (`UNAVAILABLE`). The frame names the document by its exact length and its SHA-256 and never carries it: the host passes the document beside the frame, borrowed for the call only, and nothing keeps it. The digest binds the document to the frame bytes, so the replay cache's byte comparison covers it: a retry with the same frame bytes answers the cached reply before the document is read (so a retry needs no document), and the same request ID naming another document is `REQUEST_ID_REUSE`.

After the transaction's replay preflight, exact-revision check and output reservation, the control plane checks, in order, the document's length against `document-bytes`, the length against the boot's `maximum_document_bytes` (zero is unbounded), the SHA-256 against `document-sha256`, then parses the document and compiles it under the committed store's caps, which validates it as a boot would. The diff is one whole-entity edit per entity whose bits differ (a zero's sign counts; `PartialEq` is never the test), in the order: session-level setters; removals of routes, automation, VCAs, tracks, submixes, outputs, sources; `SetConsole`; upserts of sources, outputs, submixes, tracks, VCAs, routes, automation; one `SetControl` per changed session smoothing row when the document's arm is explicit. The revision and the schema version are not diffed. No edit checks a reference when applied, so a document that removes a source and the track that reads it is accepted. The replace's preparation then sets the document's `control_smoothing` whole (an absent or `default` arm is the session default), since no edit writes the default arm back; the edit count is the diff's, so a replace that changes only the smoothing commits with zero operations. The edits take the transaction path from there: the edit-count limit, the live commit or the rebuild, the rate and quantum refusal (`control.apply.reprepare_required`), the supersession of a pending candidate (#1310), the plan admission and one `SESSION_COMMITTED` whose operation count is the reply's `applied-operations`. The reply is never `monitor`: a document carries no solo and the monitor overlay is kept.

A document that is the committed model (the revision aside) commits nothing: the reply is OK with `applied-operations` 0, edit path `unchanged` (5) and the unchanged revision, no `SESSION_COMMITTED` is queued and no plan is prepared. Every refusal happens before anything is prepared and leaves the revision, the model and the rendered bits as they were, with no event: no document or a document of another length is `INVALID_FIELD` `session.replace.document_length`; one longer than `maximum_document_bytes` is `LIMIT_EXCEEDED` `session.replace.document_too_large`; another digest is `INVALID_FIELD` `session.replace.document_digest`; a document that is not UTF-8 is `VALIDATION_FAILED` `session.replace.document_utf8`, and one that does not parse or validate is `VALIDATION_FAILED` with the session's diagnostics (no operation index). Too many edits, a stale revision and a rate or quantum change are refused as a transaction's. The OK reply is written only after the commit, and no queue is added: an ack never precedes a drop.

## The response preview (decision 17, C13, #1573)

`RESPONSE_GET` is a read of the committed model: it writes no session, revision, catalog or cell, and an exact replay returns the cached bytes without preparing an owner. On a session endpoint the sample rate and the render quantum are the committed session's, never the request's (`response.rate.session`), so the same request gives the same curves the browser gives at that rate. The provider sizes the reply from its shape (`response_result_encoded_len`) after the owner is prepared and before any curve is computed, and refuses a reply that would exceed the smaller of the endpoint's frame limit, the replay cache's response bound and the request's `maximum-reply-bytes`; the controller checks the reply it is given against the response bound again, so no provider can cache an oversized reply. Every refusal is a typed status with one error diagnostic that carries its code, and changes nothing.

An address target (#1575) is resolved on demand from the committed model the controller hands the provider: the strip's input-filter cutoffs, or its console entry's or insert's values as a rebuild prepares them (`effect_compiler::resolve_initial_values`), with the request's overrides checked by the one control validator and applied over them. A live edit therefore changes the next reply at once, before render reaches it, and the reply carries the committed revision; render reaches the same values at the applied-revision watermark. No catalog, handle or prepared owner outlives the request, so a structural edit needs no invalidation.

### The track response (#1578; decision 17, C1 and C13)

A strip target (`3:strip-id`) asks for the applied response of one track or submix: the combined curve of its input filters and EQs from the values its plan renders, and the owners that make it. It is not a read of the committed model. The provider checks the request (the core's checks, then `response.rate.session`), refuses an unknown strip (`NOT_FOUND` `control.address.unknown`) and a request whose event bound (`response_ready_encoded_bound` at the strip's owner count) exceeds the smaller of the endpoint's frame limit and `maximum-reply-bytes` (`LIMIT_EXCEEDED` `response.reply_too_large`), and only then arms the session's one capture; the reply is the capture's `request-tag`, written after the capture's job is in the render queue. The result is captured after the first successful render block of the newest plan the session had when the request was served (a rebuild or a supersession arms it again from the plan that replaced it), and arrives as one reliable `RESPONSE_READY` (`8040`) event carrying the tag. A host that does not render and service the session does not get it.

**One in flight, exactly one event.** A session has one capture: while one is in flight, or its event has not reached the host, a strip request is `BACKPRESSURE` `response.capture.pending` (backpressure queue kind `8`, capacity 1) and arms nothing. Every request answered with a tag gets exactly one `RESPONSE_READY`, never none and never two: `OK` with the capture, or a refusal: `NOT_FOUND` `response.strip.removed` (the strip left the session before a plan that holds it rendered), `UNAVAILABLE` `response.effect.unsupported`, `LIMIT_EXCEEDED` `response.limit` (a capacity bound), `INTERNAL` `response.capture`, and `LIMIT_EXCEEDED` `response.reply_too_large` should a rebuild have grown the strip past the frame limit after the request. A full reliable event queue, an outstanding structural transaction or an unread earlier event delays the event to a later `service`; nothing drops it. The capture is released, so the next strip request can arm, once its event's frame has reached the host. A replayed request returns the cached tag and arms nothing; a configuration or address target is not a capture and is served while one is in flight.

## Monitor state: the spectrum taps (#1594; decision 17, C9)

`SPECTRUM_CONFIGURE` (`0010`) sets, changes or removes the session's spectrum taps while it plays. The taps are monitor state, as the solo is: not in the session model, never in a snapshot or saved document, and they spend no revision. The session executes the command, not the protocol's one-call path (`UNAVAILABLE` there): the controller decodes and checks the frame, plans its replay entry and hands the session a `PreparedCommandFrame::Session`, which the session completes with its reply or a typed refusal, recorded for replay in the same call. An exact replay answers the same bytes and prepares nothing.

Every check runs before any write: the codec, the form rules (`INVALID_FIELD` with the request's code), each target a strip or an output of the committed model (`NOT_FOUND`, `spectrum.target.unknown`), no entry twice (`VALIDATION_FAILED`, `spectrum.duplicate`), then the preparation and the resource admission (`LIMIT_EXCEEDED` with the preparation's or resource's code). A refusal changes nothing. Then:

- An equal configuration changes nothing: `rebuild` false and both epochs unchanged.
- A change of only the hop or the budget publishes no plan. The configuration is stored and both epochs advance by one together. The hop applies at the next stream start; a running stream keeps its cadence. A budget below what the captures retain is `LIMIT_EXCEEDED` (`spectrum.budget.retained`).
- Any change of the form or the entries is a monitor rebuild: the committed model is prepared again with the new taps as a successor of the newest plan, at the committed revision (which may be 0). Taps that stay carry their window and history. No stamp is taken, no `SESSION_COMMITTED` follows, and the candidate's revision gate publishes the committed revision only when it is above 0, so render reports the same revision at adoption and the watermark does not move; its candidate completes `EXACT` with nothing superseded, so its claim adds nothing to the next revision's advance. A pending candidate is superseded first, as a transaction supersedes one: its edits are in the committed model the successor is compiled from, and a refusal publishes it again whole.

The watermark cannot report a monitor rebuild, because no revision advances. The reply names the configuration it set (`configured-epoch`), the one the running plan carries (`adopted-epoch`) and, for a rebuild, the plan (`plan-epoch`). The configuration is in effect when a later reply's `adopted-epoch` equals the `configured-epoch`; any command runs the session's service step, which promotes an adopted candidate, so polling needs no new call. Until #1595's second slice sets capability bit 16, `0010` is served but no endpoint lists it.

## Reading the spectrum: `SPECTRUM_CAPTURE` (#1595; decision 17, C13)

`SPECTRUM_CAPTURE` (`0011`) is the one-shot read of the taps, executed by the session on the monitor's service as `0010` is. `arm` arms the selected capture for its next complete window, `cancel` gives the arm up, `select` chooses one exact entry of a collection, and each answers `done`. A `read` answers `pending` until the window is complete, then pops it and answers `ready` with the window analyzed into dB bins (`SpectrumAnalysis::analyze_into`, the same analysis every host uses). The analysis runs on the thread that calls `submit_command`, the control thread, never in render; it pops the window into, and analyzes it into, one slot the monitor allocated with its service, so a read allocates only its reply. Reads are pulls: no event announces a window.

**A read never consumes what it cannot deliver.** Before it pops, a read measures with the codec the frame a ready reply of its shape takes (the requested channels, the window if asked, the selected target's identity) and refuses `LIMIT_EXCEEDED` (`spectrum.frame`) when it exceeds the session's frame limit; the window stays queued and the token does not advance. The caller's output is already reserved for a frame of that limit before the session runs (`BUFFER_TOO_SMALL` otherwise, with nothing dispatched), so a measured reply always fits. A configure refuses (`LIMIT_EXCEEDED`, `spectrum.frame`) a tap whose one-plane read (a one-shot read without the window, or a stream read, the larger) the frame limit cannot carry, since every read of it would be refused; a boot configuration with such a tap is refused too. One refusal comes after the pop: an analyzer refusal of the popped window (`UNAVAILABLE`, `spectrum.window.invalid`, which finite samples too large for the transform can cause) has consumed the window and ended the arm; the caller arms again. [Sizing](CONTROL_PROTOCOL_SIZING.md#byte-calculations) gives the frame sizes.

Each refusal is the service's error with its `code()` and one status, and it changes no service state: `spectrum.unprepared` and `spectrum.entry.unknown` are `NOT_FOUND`; `spectrum.busy` is `BACKPRESSURE`; `spectrum.capture.dropped` (an arm a plan swap dropped, answered once), `spectrum.capture.invalid` and `spectrum.window.invalid` are `UNAVAILABLE`; `spectrum.exhausted` is `LIMIT_EXCEEDED`; `spectrum.select.single`, `spectrum.not_armed`, `spectrum.channels`, `spectrum.stream.active`, `spectrum.stream.inactive`, `spectrum.cadence.rate` and `spectrum.cadence.shape` are `VALIDATION_FAILED`; a request error and `spectrum.smoothing` are `INVALID_FIELD`. A reply or refusal is recorded for replay in the call that writes it, so an exact replay of a ready read returns the same bytes and pops nothing; a host that reads often gives each read a new request ID.

## Reading the stream: `SPECTRUM_STREAM` (#1595; decision 17, C13)

`SPECTRUM_STREAM` (`0012`) is the continuous read of the taps, on the same service and its analysis. `start` starts the stream on the selected entry with a smoothing; `select` chooses one exact entry of a collection (with a stream running it restarts the stream on the entry, and a smoothing given changes it; without one a smoothing is `spectrum.stream.inactive`); `reset` resets the smoothing history without stopping the stream; `stop` stops it. Each answers the stream's metadata after the operation. A `read` answers the stream's status, and none is a refusal: `inactive`, `warming`, `pending`, `gap` (the bounded queue dropped windows: `dropped-captures` counts them, and the history is reset), `failed`, `stopped`, or `ready` with the held window analyzed with the stream's smoothing (`SpectrumAnalysis::analyze_stream_into`, the same analysis every host uses) into the monitor's one result. The analysis runs on the thread that calls `submit_command`, never in render. Only a read answers `ready`: after a ready read, a `reset` discards the window at hand and answers `pending`.

**A stream read never consumes what it cannot deliver.** The configure and the boot admit only taps whose stream read (of the tap's own channels) fits the session's frame limit ([sizing](CONTROL_PROTOCOL_SIZING.md#byte-calculations)), so every accepted entry's ready reply fits and a `gap` read delivers its `dropped-captures`. In depth, a read also measures with the codec the frame a ready reply of the selected entry takes before it reads and refuses `LIMIT_EXCEEDED` (`spectrum.frame`) when it exceeds the limit; such a read pops no window and consumes no `gap` or `failed` status. As for a capture, an analyzer refusal of the popped window (`UNAVAILABLE`, `spectrum.window.invalid`) is the one refusal after the pop, and a refusal (the same table) changes no service state.

## The output loudness meter: `LOUDNESS` (#2115)

`LOUDNESS` (`0014`) reads the session's one output loudness meter, the output peak meter's twin at the rendered master pair. It is monitor state, as the spectrum is: never saved, in no revision and no snapshot. The meter is made once per session at boot (its render half beside the output meter in the session's plan state, its control half in the session) and is part of no plan, so no operation rebuilds a plan and a plan swap carries it. While it is disarmed render pays one gate load per block.

- `start` restarts the analysis (every window, histogram, maximum and true peak) and arms the meter from the session's render position: the first block at or after it restarts the render half there, which is the origin of the 10 ms hop grid. A `start` while armed is refused (`VALIDATION_FAILED`, `loudness.active`) and changes nothing.
- `read` drains every delivered hop into the analysis, then answers.
- `reset` drains, then restarts integration (I, LRA, the maxima, the true peak since reset and the sanitized count) at the latest render sample the session has seen; `integrating-since` becomes the first hop boundary at or after it once a hop there is delivered. M and S keep running. Render is untouched.
- `stop` drains, then disarms; the readings since the last reset stay readable, and `armed` is false. A `stop` or a `read` while disarmed is allowed.

Every reply is the meter's state after the operation, and the session's service step drains the meter too, so a read is current. The render clock the meter observes is monotone on both hosts: a block renders only at the plan's own clock, a plan swap continues it, and a session seek moves source time, not the render clock. A seek is therefore a content change, not a gap: integration continues across it, and a host that wants a fresh measure after a seek sends `reset`. A hop whose first sample does not continue the last delivered hop (a hop the queue dropped) is a gap: M, S and the block assembly restart at it.

**Acked-batch question: can an ack ever precede a drop? No.** `start` acknowledges the arming only, never a delivery. A hop is dropped on render, when the record queue (512 hops) is full, before any reply can mention it, and render counts it; a reply reports only hops already drained into the analysis and carries the exact count, `hops-dropped`, which is monotone over the session's life, so a reader that wants the drops of an interval diffs two replies. A `reset` or a `stop` changes only control state. Each hop carries the arming it was observed under, and the session ingests only hops of its current arming, so a block in flight across a `stop` and a `start` never feeds the new measure.

## Automation and events

There is one way to make a change at a sample time: a stored automation edit (`SessionEdit` opcodes `0600`-`0603`), which the engine renders from the session's stored automation table (#1058). The command `AUTOMATION_ENQUEUE` (`0006`), which once admitted a batch of timed records to a queue, is **retired** (#1627, under the owner ruling in `rulings/engine-footprint-2026-09-28.md`: sample-timed delivery had no product consumer, and a host that admitted a batch acked work that no PCM reached). A frame under message ID `0006` is refused at decode as `UNSUPPORTED_MESSAGE`, before the revision check, so no revision, event, queue or replay entry changes and no ack can precede a drop; no endpoint lists `0006`, flag bit 5 or the capability fields that described its admission (9, 12, 19 and 20), and statuses 15 (`TIME_IN_PAST`) and 16 (`AUTOMATION_ORDER`) are retired with it. Every retired code is refused, never reallocated and never renumbered (see the [registry](CONTROL_PROTOCOL_REGISTRY.md)). The `Step`, `Linear` and `Exponential` span kinds and the `Sample` automation rate are retired with it (#1636, `EFFECT_CONTRACT_V1.md`, "V1 runtime automation").

**Delivery history (v1).** The delivery of the command was planned by #140, descoped by the owner ruling in `rulings/engine-footprint-2026-09-28.md`, and its unwired partial implementation (the #460 delivery service, its controller facade and the host-core builtin-batch and scalar-point endpoints) was deleted by #1056. #1315 then refused the command `UNAVAILABLE` on both hosts behind a provider feature switch that nothing set; #1627 retired the command and removed the switch. Two outcomes have their own owners instead. Rendering the session's stored automation table is #1058. Live value edits on the C ABI are delivered by #1053: a committed `SESSION_TRANSACTION_APPLY` whose delta is only live values is lowered onto the running plan's live-control lanes, with the same response and events as before. The live values are a track's fader, mute and pan or matrix values (#1257); a changed value of a track effect parameter whose `automation_rate` is `Block`, on a console-slot entry or an insert (#1264), the parametric EQ's live parameters included, which ride prepared targets (#1265); and a track effect's bypass, except the multiband compressor's, which rebuilds (#1266; the delay's is live since #1339). A transaction that changes only the session ID, a profile's id or a stored automation entry on a row that does not render yet commits with no replacement and no live value (#1260). A stored fader automation edit (an entry on a strip's `fader_db` added, removed, retargeted or given other segments) is a rebuild that carries every owner (#1648); a static fader value of a lane the session automates is that lane's fallback, not a control value, so a change of it is a structure rebuild (#1650b; #1648 D3), and a `SET_CONTROL fader_db` on that lane writes the entry's hand offset, a live value heard on top of the curve (#1650); every other row stays model-only until its rendering slice adds it. Every other transaction still replaces the plan, including every submix strip value (#1053 G1), any edit while a VCA is declared (G3) and a mute change on a track that a `follows_mute` route reads (G2) (`C_ABI_V1_QUALIFICATION.md`, "Value-only track edits on the running plan" and the sections after it).

**Sources across a structural transaction.** A committed transaction that replaces the plan does not reset the sources it leaves unchanged. On the C ABI (#1273) such a source keeps its ring, generation and read position across the plan swap; source submissions and seeks address the newest committed session from the commit on, so a host keeps feeding the source contiguously and must not reseek it. PCM is never part of the protocol, so the transaction acknowledges no PCM: PCM already accepted for a source the transaction removed is discarded with its plan, and later submissions for it are refused as `source.id.unknown`. An added source starts at generation 1, frame 0, until the host seeks it; a source whose declaration the transaction changed restarts the same way, in a new ring at generation 1, frame 0, with the PCM accepted for it before the commit discarded with its plan, so the host restarts its feed.

Changing revision cancels nothing, and the transport has no position to locate (#1635 retired the stored transport position). The event `AUTOMATION_CANCELED` (`8002`) is **retired** with the command that filled the queue it reported on (#1628; `AUTOMATION_ENQUEUE` is retired, #1627, so no batch is ever accepted and none can be dropped), and a frame under `8002` is refused at decode like any retired ID. A transaction commit reserves only its `SESSION_COMMITTED`; a transport set reserves only its `TRANSPORT_STATE`. `SESSION_COMMITTED`, transport state, and diagnostics are reliable; meter batches and periodic counter snapshots are the only lossy events. A reliable event has a monotonic sequence and queue capacity is reserved before its related commit.

**Observation subscriptions (#1584, decision 17, C9).** The `Observe` edit (`0801`) is a monitor edit, as a solo is: a transaction of monitor edits only keeps the committed revision, emits no `SESSION_COMMITTED` and replies edit path `4`, monitor; an exact replay answers the same bytes and queues nothing. A subscription is not a value: it has no control row, is never saved and never in a snapshot. Each `Observe` is checked inside the transaction at its place, against the candidate model, so an edit after an `UpsertTrack` or `PutTrackEffect` of the same transaction can name the new effect; a refusal refuses the whole transaction with `VALIDATION_FAILED` and a diagnostic at `edits[i]`: `observation.address.unknown` (no such strip, console slot or insert), `observation.tap.unknown` (no declared tap with that ID; `0` included), `observation.tap.unsupported` (a declared tap that is not resident), `observation.window` (`window_blocks` above 4096). Subscribers share one arm per tap: an arm of an unarmed tap binds it with one subscriber, an arm with the same window (the value asked for; `0` is one value) adds one and queues nothing, an arm with another window is `observation.window_conflict`, a disarm removes one subscriber and queues the disarm only when the last leaves. A disarm names the arm it ends by its tag, the tag that arm's reply gave (#2087): a disarm whose tag is the bound arm's applies as above, and one whose window is not the bound arm's is `observation.not_subscribed`; a tag the host never issued (`0`, or at or above its next tag) is `observation.not_subscribed`; any other tag names an arm the host already ended (a removed effect, perhaps added back and armed again by another subscriber), and the disarm changes nothing: no binding moves, no record is queued, the transaction commits, and the reply reports the binding the transaction began with. An `OBSERVATION_ENDED` event can reach a subscriber after later commits (in the browser it comes by message), so a subscriber that closes before it sees the end cannot silence a later subscriber of the same tap. A transaction queues at most one record per tap, its net change (a disarm and an arm with another window are one re-arm, which restarts the window). The records are admitted (one naming per tap, the ended event's frame, the queue room) before anything is written and queued after the commit, before the reply: a queue without room for them refuses the transaction as retryable `BACKPRESSURE` with nothing changed. In a structural transaction the records go to the successor plan's own queues, never the predecessor's; a tap the successor carries takes its predecessor's state at the swap and then applies the record. A host whose adapter does not serve the edit refuses every `Observe` with `observation.unavailable`; both hosts serve it, because every plan binds every declared tap (#1590 D5). Each queued record carries an arm tag (#1585 D4, D5): the host's one counter issues it, from `1`, one more per record, so tags are monotone per session and `0` is never one. A transaction's records are tagged in key order when it is prepared, and the counter moves past them only when it commits, so a refused transaction issues none. The reply lists one tag per `Observe` edit in transaction order (`TransactionApplied` field `3`): an edit that keeps the binding the transaction began with (a second subscriber's arm, or a disarm that leaves a subscriber) reports that binding's tag; every other edit reports the tag of the record the transaction queues for its tap (an arm, a re-arm, or the last subscriber's disarm), or, when the transaction leaves the tap as it found it, the tag of the binding it began with (`0` when it began unbound). A commit that ends bindings lists their tags in key order (field `4`). An `Observe` is in effect when a read of the tap reports it armed with that tag (the observation read, #1586), not when the reply returns: the reply says which record to wait for.

**Observation read (#1586, decision 17, C1 and C13).** `OBSERVATION_READ` (`000f`) reads the latest window of 1 to 256 taps, each named by its strip, its console slot or insert and its tap ID, on the plan render runs. A read never consumes and never arms: it reads each tap's slot without acknowledging it, so the meter fold still folds the same window and two reads with no render between them answer the same rows. Each row's status follows #1585's contract: **unarmed** when the tap's last issued record is a disarm (in effect when it is accepted) or the slot reads unarmed; **ready** when the slot is armed with a tag at or above the last issued one and its window opened at or after the arm sample (the row then carries the window, its span, sequence and blocks, and the asked-for lanes in the tap's native unit); **pending** otherwise: an arm render has not applied (the slot's tag is below the issued tag), an armed tap with no window since its arm, or a read that tore on every attempt. A row's `armed`, `arm-sample` and `arm-tag` are what render applied: a row never claims an arm render has not applied. The batch is checked whole before any row is written, and a refusal answers no row: a reply whose widest form (every row ready with both lanes) exceeds the control frame limit is `LIMIT_EXCEEDED` `observation.frame`; then, at the first selection that fails, at `selection[i]`: `NOT_FOUND` `observation.address.unknown` (no such strip, console slot or insert on the running plan), `NOT_FOUND` `observation.tap.unknown` (no declared tap with that ID), `UNAVAILABLE` `observation.tap.unsupported` (a computed tap), `UNAVAILABLE` `observation.unbound` (an effect with no observation lane), `INVALID_FIELD` `observation.selection.duplicate` (an earlier selection names the same address and tap, whatever its lanes). A refusal is cached for exact replay like a reply. A read allocates nothing per row: the C ABI keeps each plan's index of its effect instances by stable key with its epoch and the session's row table from boot.

**Observation subscriptions across a rebuild (#1584).** A host that keeps observation subscriptions (both hosts, through the `Observe` edit, above) holds a table of armed taps beside its monitor overlay and apart from it: host-local, never saved, never in a snapshot, with no revision. A subscription is acknowledged when its record is queued on the newest plan, and the table is written with that acknowledgement. Every plan the host prepares after a rebuild is prepared from the table, so a tap whose effect restarts (a prepared change such as the link mode) is armed in the successor and opens its first window at the successor's first rendered block, as a record applied at that block would; a tap whose effect carries keeps its own window and sequence, and the prepared arm never restarts it. No acknowledged subscription is dropped at a swap. A rebuild that removes the effect (the insert, the strip or the console slot is gone, or the ID now names an effect without that resident tap) ends the binding: the commit queues one reliable `OBSERVATION_ENDED` (`8011`) after the transaction's `SESSION_COMMITTED`, at the committing revision, carrying the stable key of every binding that commit ended, in key order, however many there are. The room for this one event is reserved with the commit's own before anything is prepared or published; if the reliable lane holds unread events that leave no room for both, the transaction is refused as `BACKPRESSURE` with the model, the revision, the table and the plan unchanged, and the same request commits after the lane drains. The number of keys never changes the room needed. The table is bounded so that this event always fits (#1676, #1685): a subscription is admitted only while the one `OBSERVATION_ENDED` frame that would carry the key of every armed tap, measured by its exact encoded bytes with the taps' real strip and effect IDs, fits within the control frame limit. A key takes at least 80 encoded bytes and grows with its IDs, so the browser's 16 KiB frame holds a meter tap on every insert of a 64-track session with short IDs. A subscription whose arm would make the event outgrow the frame is refused before it is acknowledged, with nothing queued and no state moved (the transaction is refused as the resource limit `capi.resource.limit` on both hosts, and the SDK names it `observationLimit`; it is never backpressure, because no render makes room: unsubscribe a tap first). The core's `Observe` edit admits the transaction's net changes, checks the queue room and only then queues them, computing each key's size from its two ID lengths without allocating, so no record is queued without the frame check. A valid removal therefore never meets an unsendable event; the resource-limit refusal for an event over one control frame stays as a defence only. The memory reserved for the event follows the observation slots the session has had, bounded by what the admitted keys' encoded bytes allow them to own. Both hosts run the one control plane, so the browser and the C ABI emit the same event for the same transaction.

## Queues and telemetry

Control commands, responses, and reliable events reject before related state changes when full and preserve the original item. Telemetry may replace only the latest same `(revision, handle/component)` value, incrementing `telemetry_coalesced`; a new key rejected at capacity increments `telemetry_dropped`. Counters are non-resetting and saturate at `u64::MAX`.

Render-side consumption has a fixed work bound and does no BTLV decode, allocation/free, lock, logging, I/O, syscall, or structural mutation. Queue configuration and formulas are in the [sizing guide](CONTROL_PROTOCOL_SIZING.md). Typed `BACKPRESSURE` identifies queue kind, capacity, pre-attempt occupancy, requested slots, generation, and applicable byte/retry values.

## Snapshots, telemetry, and deferred ownership

Snapshot chunks form canonical UTF-8 only when reassembled; a chunk may split a code point. An any-revision first page returns its observed revision; continuations are exact or conflict. Control handles are scoped to a structure (`structure_epoch`) and never renderer parameter slots. Meter handles are configuration-scoped: the 1-based index of a `TELEMETRY_CONFIGURE` meter table entry (#1583 D1), which names the output or a strip by its stable ID, so a structural commit never moves a handle; an entry whose strip the adopted plan does not have stays in the table and reports no valid record until a commit brings the ID back. `CONTROL_LIST_GET` and `CONTROL_STATE_GET` page the control list by cursor and limit, optionally of one owner and optionally of the header rows alone (`headers_only`, #2206: the strip order and each strip's sections without the control descriptors); a page read at a structure that is no longer current is `REVISION_CONFLICT` with the diagnostic `control.list.stale`, and the caller restarts from handle `0`. The retired `PARAMETER_METADATA_GET` and `PARAMETER_STATE_GET` (`0004`, `0005`) are refused as `UNSUPPORTED_MESSAGE` and never reallocated. Telemetry configuration is endpoint-local and all or nothing (#1351 D2, #1583 D3): a refusal keeps the stored configuration. In order, a strip entry whose ID is no strip of the committed model is `NOT_FOUND` `meter.strip.unknown` at `meters[i]`; an endpoint with no meter delivery (the browser, until #1588) refuses any entry as `UNAVAILABLE` `meter.unavailable`; a meter period that is not a positive multiple of the meter window is `INVALID_FIELD` `meter.period`; and, until #1587, a gain-reduction entry is `UNAVAILABLE` `meter.gain_reduction.unavailable` and a strip peak entry `UNAVAILABLE` `meter.strip.unavailable`. An empty table is always accepted, so counters and diagnostics are configured on every host, and the echo carries the meter window in blocks when the endpoint has a meter delivery. Each `METER_BATCH` is one closed batch of `meter_period_blocks / meter_window_blocks` consecutive meter windows: its span is the first window's start to the last window's end, its peaks are their maxima, and its sequence counts batches from `1` after each accepted configuration. Records follow the table order; an output peak entry gives a left and a right record, with `VALID`, and `CLIPPED` when the value is above `1.0`. A batch is lossy telemetry: a window that never reaches one (the delivery's losses, and a partial batch a gap in the windows discards) adds to `METER_WINDOWS_LOST` (22), and a sequence never skips. Providers return typed bounded records, and adapters own transport framing; their boundary is [documented here](CONTROL_PROVIDER_BOUNDARY.md).
