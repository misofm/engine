# MISO control protocol semantics

This defines controller behavior for the [BTLV bytes](CONTROL_BTLV_V1.md) and [registry](CONTROL_PROTOCOL_REGISTRY.md). It does not publish a plan, execute a seek, define DSP parameter meanings, or transport PCM.

## Revision, transaction, and replay

The committed `SessionModel` owns its revision, and the revision lies in `0..=9223372036854775807` (2^63 - 1, the session schema's domain; the wire field stays `u64`); command `revision-any` is therefore the header flag plus a zero carrier, never a revision sentinel. Structural edits require an exact revision and at least one edit; a configured zero edit limit disables the transaction command and its paired session events in capabilities and dispatch. Transactions clone/apply/compile a candidate typed session and replace `(SessionModel, CompiledSession, SessionRevision)` only when all validation, capacity reservation, and compilation steps succeed. One success increments once; malformed input, empty input, validation/compile/resource failure, backpressure, and replay leave model and revision untouched. A mutation at revision 2^63 - 1 returns `REVISION_EXHAUSTED` before the candidate is built; the controller does not turn a compiled session into a `PreparedRenderPlan`.

A transaction that needs a new plan while an earlier one's replacement plan is still unadopted commits as any other (#1310): the host takes the waiting replacement back, prepares one successor of the running plan that carries both, and publishes it, or, should the new transaction be refused, publishes the waiting replacement again unchanged. Host-fed sources the earlier transaction added keep their accepted PCM and queued seeks. No accepted chunk is dropped across a supersession: when the waiting replacement created a source's ring (the earlier transaction added the source, or redeclared it) and the host has fed that ring (a chunk, a seek or an end of region), a new transaction that does not keep the source as the replacement declares it (it declares it as the running plan does, redeclares it another way, or removes it) is refused with backpressure before it commits. Nothing changes (the replacement stays published, no event, no revision), and a retry after render adopts the replacement commits. A host that does not render keeps getting backpressure for such a transaction until it renders. A source the replacement carries unchanged from the running plan is not refused this way. Every case stays refused, the one where the new transaction declares the source as the running plan does included (#1698): the host restarted its feed of the source against the waiting replacement, so the successor starts the source fresh and cannot play that replacement's chunks; the cases stay refused until an issue lets the successor read those chunks or the owner rules that a removed source's chunks may drop. Everything else the new transaction leaves as the running plan has it (a strip, an effect, a meter) carries from the running plan as one direct transaction would carry it, also when the waiting replacement had restarted or removed it (#1698). A source the caller's own transaction removes discards its queued audio, whether the running plan or the waiting replacement (carrying it unchanged from the running plan) holds it: the caller asked for the removal, so this is not an unintended drop. No counter or telemetry field reports those frames (source telemetry leaves with the source; the watermark outcome flags and the session counters name none); a counter for the discarded frames is a successor issue (placeholder #1699). The applied-revision watermark completes the displaced revisions as `superseded` when the successor is adopted. The resource admission counts every plan the session still holds (the running plan, the waiting replacement, and a plan render has displaced until the service step reclaims it) and the successor. A resource refusal is backpressure when the successor fit against the newest held plan alone, so a retry after a render normally commits; the split is approximate, and such a retry may still be refused within a small band (a successor prepared on the adopted replacement differs by a few hundred bytes from one prepared across it). It is a compile rejection when the successor does not fit even then.

All v1 operations are absolute and idempotent. A new logical command has a nonzero, strictly increasing endpoint-local request ID. The bounded replay cache stores exact canonical request and response bytes. Identical repeated bytes return the cached response without execution; same ID with changed bytes returns `REQUEST_ID_REUSE`; evicted/retired IDs return `REPLAY_EXPIRED`. Completed backpressure is replayed too, so retrying it uses a new ID. Cache capacity is reserved before execution; an unretainable response is rejected before state changes. The guarantee ends with the endpoint lifetime; reconnect recovery belongs to an adapter.

## The response preview (decision 17, C13, #1573)

`RESPONSE_GET` is a read of the committed model: it writes no session, revision, catalog or cell, and an exact replay returns the cached bytes without preparing an owner. On a session endpoint the sample rate and the render quantum are the committed session's, never the request's (`response.rate.session`), so the same request gives the same curves the browser gives at that rate. The provider sizes the reply from its shape (`response_result_encoded_len`) after the owner is prepared and before any curve is computed, and refuses a reply that would exceed the smaller of the endpoint's frame limit, the replay cache's response bound and the request's `maximum-reply-bytes`; the controller checks the reply it is given against the response bound again, so no provider can cache an oversized reply. Every refusal is a typed status with one error diagnostic that carries its code, and changes nothing.

## Automation and events

There is one way to make a change at a sample time: a stored automation edit (`SessionEdit` opcodes `0600`-`0603`), which the engine renders from the session's stored automation table (#1058). The command `AUTOMATION_ENQUEUE` (`0006`), which once admitted a batch of timed records to a queue, is **retired** (#1627, under the owner ruling in `rulings/engine-footprint-2026-09-28.md`: sample-timed delivery had no product consumer, and a host that admitted a batch acked work that no PCM reached). A frame under message ID `0006` is refused at decode as `UNSUPPORTED_MESSAGE`, before the revision check, so no revision, event, queue or replay entry changes and no ack can precede a drop; no endpoint lists `0006`, flag bit 5 or the capability fields that described its admission (9, 12, 19 and 20), and statuses 15 (`TIME_IN_PAST`) and 16 (`AUTOMATION_ORDER`) are retired with it. Every retired code is refused, never reallocated and never renumbered (see the [registry](CONTROL_PROTOCOL_REGISTRY.md)). The `Step`, `Linear` and `Exponential` span kinds and the `Sample` automation rate are retired with it (#1636, `EFFECT_CONTRACT_V1.md`, "V1 runtime automation").

**Delivery history (v1).** The delivery of the command was planned by #140, descoped by the owner ruling in `rulings/engine-footprint-2026-09-28.md`, and its unwired partial implementation (the #460 delivery service, its controller facade and the host-core builtin-batch and scalar-point endpoints) was deleted by #1056. #1315 then refused the command `UNAVAILABLE` on both hosts behind a provider feature switch that nothing set; #1627 retired the command and removed the switch. Two outcomes have their own owners instead. Rendering the session's stored automation table is #1058. Live value edits on the C ABI are delivered by #1053: a committed `SESSION_TRANSACTION_APPLY` whose delta is only live values is lowered onto the running plan's live-control lanes, with the same response and events as before. The live values are a track's fader, mute and pan or matrix values (#1257); a changed value of a track effect parameter whose `automation_rate` is `Block`, on a console-slot entry or an insert (#1264), the parametric EQ's live parameters included, which ride prepared targets (#1265); and a track effect's bypass, except the delay's and the multiband compressor's, which rebuild (#1266). A transaction that changes only the session ID, a profile's id or a stored automation entry on a row that does not render yet commits with no replacement and no live value (#1260). A stored fader automation edit (an entry on a strip's `fader_db` added, removed, retargeted or given other segments) is a rebuild that carries every owner (#1648); a static fader value of a lane the session automates is that lane's fallback and gives no live record (#1648 D3), and a `SET_CONTROL fader_db` on that lane writes the entry's hand offset, a live value heard on top of the curve (#1650); every other row stays model-only until its rendering slice adds it. Every other transaction still replaces the plan, including every submix strip value (#1053 G1), any edit while a VCA is declared (G3) and a mute change on a track that a `follows_mute` route reads (G2) (`C_ABI_V1_QUALIFICATION.md`, "Value-only track edits on the running plan" and the sections after it).

**Sources across a structural transaction.** A committed transaction that replaces the plan does not reset the sources it leaves unchanged. On the C ABI (#1273) such a source keeps its ring, generation and read position across the plan swap; source submissions and seeks address the newest committed session from the commit on, so a host keeps feeding the source contiguously and must not reseek it. PCM is never part of the protocol, so the transaction acknowledges no PCM: PCM already accepted for a source the transaction removed is discarded with its plan, and later submissions for it are refused as `source.id.unknown`. An added source starts at generation 1, frame 0, until the host seeks it; a source whose declaration the transaction changed restarts the same way, in a new ring at generation 1, frame 0, with the PCM accepted for it before the commit discarded with its plan, so the host restarts its feed.

Changing revision cancels nothing, and the transport has no position to locate (#1635 retired the stored transport position). The event `AUTOMATION_CANCELED` (`8002`) is **retired** with the command that filled the queue it reported on (#1628; `AUTOMATION_ENQUEUE` is retired, #1627, so no batch is ever accepted and none can be dropped), and a frame under `8002` is refused at decode like any retired ID. A transaction commit reserves only its `SESSION_COMMITTED`; a transport set reserves only its `TRANSPORT_STATE`. `SESSION_COMMITTED`, transport state, and diagnostics are reliable; meter batches and periodic counter snapshots are the only lossy events. A reliable event has a monotonic sequence and queue capacity is reserved before its related commit.

**Observation subscriptions across a rebuild (#1584).** A host that keeps observation subscriptions (the browser's observe kinds on the engine-wide control plane; the C ABI's own edit follows) holds a table of armed taps beside its monitor overlay and apart from it: host-local, never saved, never in a snapshot, with no revision. A subscription is acknowledged when its record is queued on the newest plan, and the table is written with that acknowledgement. Every plan the host prepares after a rebuild is prepared from the table, so a tap whose effect restarts (a prepared change such as the link mode) is armed in the successor and opens its first window at the successor's first rendered block, as a record applied at that block would; a tap whose effect carries keeps its own window and sequence, and the prepared arm never restarts it. No acknowledged subscription is dropped at a swap. A rebuild that removes the effect (the insert, the strip or the console slot is gone, or the ID now names an effect without that resident tap) ends the binding: the commit queues one reliable `OBSERVATION_ENDED` (`8011`) after the transaction's `SESSION_COMMITTED`, at the committing revision, carrying the stable key of every binding that commit ended, in key order, however many there are. The room for this one event is reserved with the commit's own before anything is prepared or published; if the reliable lane holds unread events that leave no room for both, the transaction is refused as `BACKPRESSURE` with the model, the revision, the table and the plan unchanged, and the same request commits after the lane drains. The number of keys never changes the room needed. The table is bounded so that this event always fits (#1676, #1685): a subscription is admitted only while the one `OBSERVATION_ENDED` frame that would carry the key of every armed tap, measured by its exact encoded bytes with the taps' real strip and effect IDs, fits within the control frame limit. A key takes at least 80 encoded bytes and grows with its IDs, so the browser's 16 KiB frame holds a meter tap on every insert of a 64-track session with short IDs. A subscription whose arm would make the event outgrow the frame is refused before it is acknowledged, with nothing queued and no state moved (the browser reports it as `RESULT_UNSUPPORTED` with its own reason `observationLimit`, 15, at the subscription that crossed; it is never backpressure, because no render makes room: unsubscribe a tap first). The core admits, checks the queue room and queues the whole batch in one call, `admit_and_push_observation_batch`, which computes each key's size from its two ID lengths and allocates nothing, so no record is queued without the frame check. A valid removal therefore never meets an unsendable event; the resource-limit refusal for an event over one control frame stays as a defence only. The memory reserved for the event follows the observation slots the session has had, bounded by what the admitted keys' encoded bytes allow them to own. Both hosts run the one control plane, so the browser and the C ABI emit the same event for the same transaction.

## Queues and telemetry

Control commands, responses, and reliable events reject before related state changes when full and preserve the original item. Telemetry may replace only the latest same `(revision, handle/component)` value, incrementing `telemetry_coalesced`; a new key rejected at capacity increments `telemetry_dropped`. Counters are non-resetting and saturate at `u64::MAX`.

Render-side consumption has a fixed work bound and does no BTLV decode, allocation/free, lock, logging, I/O, syscall, or structural mutation. Queue configuration and formulas are in the [sizing guide](CONTROL_PROTOCOL_SIZING.md). Typed `BACKPRESSURE` identifies queue kind, capacity, pre-attempt occupancy, requested slots, generation, and applicable byte/retry values.

## Snapshots, telemetry, and deferred ownership

Snapshot chunks form canonical UTF-8 only when reassembled; a chunk may split a code point. An any-revision first page returns its observed revision; continuations are exact or conflict. Control and meter handles are scoped to a structure (`structure_epoch`) or a revision and never renderer parameter slots. `CONTROL_LIST_GET` and `CONTROL_STATE_GET` page the control list by cursor and limit; a page read at a structure that is no longer current is `REVISION_CONFLICT` with the diagnostic `control.list.stale`, and the caller restarts from handle `0`. The retired `PARAMETER_METADATA_GET` and `PARAMETER_STATE_GET` (`0004`, `0005`) are refused as `UNSUPPORTED_MESSAGE` and never reallocated. Telemetry configuration is endpoint-local. Providers return typed bounded records, and adapters own transport framing; their boundary is [documented here](CONTROL_PROVIDER_BOUNDARY.md).
