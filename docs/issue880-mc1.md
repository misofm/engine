# Issue #880 MC-1 — compressor attack/release ramp options

**Status:** decision brief ready with frozen MQ-2 evidence. No production changes or recommendation are made here. R3 remains an owner ruling.

## Baseline and MQ-2 evidence

`compressor::design::rate_coefficient` computes `c = 1 - exp(-1 / (0.001 * time_ms * Fs))` in `f64`, then rounds once to `f32`. That precision matters: at 5,000 ms and 96 kHz, `c` is about `2.08e-6`; doing the subtraction in `f32` loses most of its significant bits. `advance_ramps` runs for each active ramp sample, advances only moving parameters, and passes their parameter-index bitmask to `design_lane`. Bits 3 and 4 independently guard attack and release coefficient design; unrelated curve, makeup, and mix changes do not call `rate_coefficient`. After all ramps settle, the idle loop does no coefficient design.

MQ-2's frozen native setup is 64 tracks in eight `Simd8` banks, stereo, 48 kHz, 128 frames per call, with a 64-sample ramp. Its state proof counts the existing per-lane `math::exp` evaluations in each measured block:

| MQ-2 arm | Active time parameters | Proven baseline `exp` calls / 64-track block | Round 1 mean / max (µs) | Round 2 mean / max (µs) |
|---|---:|---:|---:|---:|
| Release only | 1 | 8,192 | 169.448 / 175.995 | 169.313 / 174.312 |
| Attack + release | 2 | 16,384 | 215.761 / 220.029 | 216.534 / 220.700 |
| No automation | 0 | 0 | 40.739 / 45.918 | 40.833 / 45.236 |

The call counts are the harness's state-derived proof, not elapsed-time estimates. Each arm has one 32-block warmup and two 32-block measured rounds. These are observed status-quo timings only; no option's projected speed is inferred from call-count ratios. The single validated invocation used candidate `e0c57d6ff959616bab23e6783a9a14585408020d` and harness SHA-256 `bf2d6604d641f7200bced4a86ce4ba41c5ba2eaf996ec1a66ec378264416e81c` on an AMD EPYC 7313P, Linux x86_64, `rustc 1.97.1`, `x86_64-unknown-linux-gnu`.

## R3 options

Cost below is render-path work for the active portion of one 64-sample ramp. Counts are per changed lane and channel unless a bank-vector call is stated; the MQ-2 setup has 64 lanes total and two channels. The event has already been validated and applied before render.

| Option | Cost | Accuracy and ramp trajectory | Rendered bits and changed-mask interaction |
|---|---|---|---|
| **(a) Coefficient-domain linear ramp** | Two exact `rate_coefficient` designs per changed attack/release lane-channel event (current value and target), then a coefficient `LinearRamp` update on each of 64 active samples. For MQ-2's all-lane event pattern, that is 256 scalar `exp` calls per changed time parameter per block, versus baseline 8,192; 512 for both parameters. Adds ramp state and sample-wise additions. | Both endpoints use the current f64 law and round once. Between them, the coefficient is linear while milliseconds currently ramp linearly; these are different trajectories. | Moving ramp samples change compressor output bits; no promise of baseline digest identity. `changed` still identifies attack/release events, but `design_lane` would need to seed/update a second coefficient ramp. Current parameter ramps remain necessary for exposed current/target semantics. The added coefficient-ramp state must be reconstructible on restore or added to the versioned payload; the present payload stores only parameter current/target/remaining and restore redesigns from current. Resets and final snap must synchronize both representations. |
| **(b) Recompute every K ramp frames, hold between** | At most `ceil(64/K)` exact `rate_coefficient` evaluations per changed lane-channel parameter per ramp, with a forced exact evaluation on sample 64. Coefficient redesigns fall by roughly K for K greater than 1; each active frame still advances its parameter ramp and performs the changed-mask checks. | Each refreshed point uses the current f64 law, but the held coefficient is a staircase approximation to the current smooth-in-milliseconds trajectory. Larger K increases hold error; endpoints can remain exact. | Bits change whenever a held interval differs from the baseline sequence. Keep `changed` lane-local and recompute only for bits 3/4. Cadence must be anchored to ramp progress (for example, `remaining`), including an exact final update, rather than each `process_block` boundary; otherwise existing partition-invariance behavior changes with host block sizes. A cadence phase not derivable from remaining must be serialized. |
| **(c) Lane-wide `expm1`** | A lane-vector design at each changed attack/release frame: up to 64 vector evaluations per bank/channel/parameter during the ramp (1,024 vector calls for one parameter, 2,048 for two in the MQ-2 topology), with the operation count and throughput dependent on the eventual approximation. This is not yet measured. | `-expm1(-1/tau_samples)` avoids cancellation for small coefficients, but MA-4 requires a Lane-only unfused implementation with full-domain accuracy, monotonicity, and scalar/Simd4/Simd8/Wasm bit-identity evidence. Agreement with the current f64 result must be proved at the long-release end; “more accurate” alone does not establish compatible `f32` words. | May change coefficient words and output bits even if closer to the mathematical value than the baseline. The scalar `design_lane` interface currently receives one lane and a scalar mask, so useful vectorization needs a lane-batched design/update path that preserves per-lane bits 3/4 and leaves unrelated words untouched. No coefficient-state or payload change is needed if only the pointwise design law changes. |
| **(d) Status quo** | One scalar f64 `exp` for each moving attack/release lane-channel on each ramp sample: 8,192 / 16,384 / 0 calls in MQ-2's three arms. No rate-coefficient work for settled lanes. | Preserves the exact f64-then-f32 law and the existing 64-sample linear-in-milliseconds parameter trajectory. | Baseline output and state bits remain unchanged. Existing `changed` mask is already the selective-work gate; restore re-derives the coefficient from restored current milliseconds, and ramp completion designs the exact target coefficient. |
| **(e) Per-process-block hold** | At most one exact coefficient design per active time-parameter lane-channel per call, if the implementation caches until the next call; for the 128-frame MQ-2 calls that is at most 128 per parameter per block for this all-lane stereo setup. If all settled lanes are also refreshed, the cost floor is instead two designs per lane-channel per call and buys no ramp-specific saving. | Holds one coefficient while milliseconds continue to ramp. This is a coarser staircase than (b) and its maximum stale interval is the caller's block length, not a fixed K. A 128-frame call is twice the entire ramp window. | Output bits change and depend on the caller's block partition unless refresh points are canonicalized independently of calls. A `changed` bit remains set on every active sample today, so simply placing `rate_coefficient` behind it still recomputes per sample; implementation needs separate dirty/refresh bookkeeping. Refreshing only at block entry from the current value can miss the target design when a 64-sample ramp completes inside a longer block, and the next block must still perform a final design. The present multi-band analogue actually plans ramp-bounded segments and its `BandCache` is keyed by current value bits; it is not evidence that arbitrary compressor calls may safely be treated as a single fixed block. |

## Shared gates and restore constraints

Options (a), (b), (c), and (e) move words or their update times during a ramp, so they need a separately reviewed bit-impact decision and must not silently re-pin compressor corpus digests. The existing compressor partition gate compares output bits and payload bytes across 1-, 7-, 63-, 64-, 65-, 127-, 128-, 129-, and 512-frame partitions. Any selected schedule must preserve that gate's invariance or explicitly obtain an owner ruling to change the contract.

The state payload is currently frozen at 22 words per channel: gain reduction plus current/target/remaining for each of seven parameter ramps. It omits `step`; restore derives `step = (target - current) / remaining` and redesigns all coefficients from the restored current values. The mid-ramp restore gate checks continuation after that reconstruction. Thus any auxiliary ramp/cadence state in (a) or (b) must be derivable from this triple with the same resumed-sample sequence, or the state-layout/version change and compatibility cost must be part of the ruling. For all options, keep the final ramp sample an exact target snap and keep reset/restore design consistent with the selected law.

The timing record passed validation and is preserved at [`artifacts/issue880-mq2/record.json`](../artifacts/issue880-mq2/record.json), with raw output at [`artifacts/issue880-mq2/raw.log`](../artifacts/issue880-mq2/raw.log). The two measured rounds are close for the two ramping arms; the no-automation arm is the same-run reference workload. This establishes the size of the observed ramp-path cost in this frozen setup, but does not isolate `exp` as the sole cause or predict the improvement from any option. These timings are descriptive evidence for R3, not an acceptance threshold; no rerun or call-count-based timing projection is warranted.
